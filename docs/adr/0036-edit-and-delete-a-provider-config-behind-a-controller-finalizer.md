# 0036. Edit and delete a provider config, behind a controller finalizer rather than a handler check

## Context

[0033](0033-create-a-provider-config-from-the-interface.md) added a second write seam, `ProviderConfigWriter`, with one method and a parameter that names the kind rather than taking a `client.Object`. It stopped at create, and said why: "a verb that moves an arbitrary field of an existing configuration is exactly the capability [0027](0027-mutating-web-interface-behind-a-typed-writer-and-a-cross-origin-guard.md) declined to add, and repointing a live provider's credentials is a larger act than creating a configuration that starts unready". The two acts it declined are not the same act, and the reason they were declined together is that neither had been thought through.

Deleting is the dangerous one, and it is dangerous in a way no seam can fix. Horizon tears a lease down with the credentials the configuration resolves. Delete the configuration while a lease still names it and the controller has nothing to call the provider with: the machines keep running and keep billing until the node-side dead man's switch of [0021](0021-node-side-dead-mans-switch-on-two-clocks.md) fires, which is the mechanism that exists precisely so that a broken control plane costs an hour rather than a month. That is the worst outcome this system has, and the interface was one `kubectl delete` away from it long before this record.

Editing is the one that reads dangerous and is not. It once was: lowering `maxLifetime` moved every derived deadline, and a deadline in the past spends the whole teardown budget before teardown starts. The fix latched the backstop per instance at creation, and `latchBackstop` still returns early the moment an instance records one, so no later edit moves a machine that is already running in either direction. Blocking edits for that reason would now be guarding against a hazard the controller has already closed, at the cost of the one operation an operator most needs during a long lease, which is rotating a credential that has been compromised or has expired.

## Decision

**The narrow seam gains two verbs, and both name what they reach.** `ProviderConfigWriter` becomes `Create(ctx, *v1alpha1.ProviderConfig)`, `Replace(ctx, name, v1alpha1.ProviderConfigSpec)` and `Delete(ctx, name)`. No parameter is a `client.Object`, no parameter is a patch, and no parameter is a field path, so the kind and the part of it each verb reaches are stated by the signature rather than held by the call sites. That is the shape [0033](0033-create-a-provider-config-from-the-interface.md) described and the correction it made to [0027](0027-mutating-web-interface-behind-a-typed-writer-and-a-cross-origin-guard.md), applied to the two verbs that were missing. `LeaseWriter` is still untouched and still unreused. A test states the three signatures as an interface and asserts it in both directions, so widening any one of them to a `client.Object` stops the package compiling rather than quietly restoring the loophole.

**The delete guard is a finalizer in the controller, not a check in the handler.** A new `ProviderConfigReconciler` puts `horizon.dev/provider-config` on every configuration, and on deletion it lists the capacity leases, refuses to release while any of them names the configuration in `spec.providerRef`, and releases once none do. The reason it lives there is that the interface is not the only client. A check in the HTTP handler is bypassed by `kubectl`, by any controller, by a GitOps reconciler and by the next interface someone writes, and the failure it would fail to prevent is machines that bill until the watchdog fires. The controller is the only place that sees every deletion whatever asked for it.

It refuses while *any* lease names the configuration rather than only an Active one. A lease that is being torn down is exactly the lease that still needs the credentials, and a lease that has not yet been accepted will need them within one reconcile, so the narrower rule would be a guarantee with a hole in the two states that matter.

The controller watches leases as well as configurations and maps a lease event to the configuration it names, so the last lease to go releases the configuration on the next pass rather than at the next resync.

**The refusal is a condition, not just a log line.** The controller sets `Deletable=False` with reason `LeasesBound` and a message naming the leases, alongside the reason constants [0029](0029-publish-provider-config-readiness-and-its-catalogue.md) established. It is written only when a deletion is refused: once the last lease goes the object is deleted, so a `Deletable=True` would never be observable and would cost a status write on every ordinary pass. `Ready` is left alone, because the catalogue refresher recomputes it on every refresh and two writers of one condition is a flap rather than a report.

**The endpoint names the bound leases rather than answering `202` for a deletion that will not happen.** `DELETE /api/providerconfigs/{name}` lists the leases first and answers `409` naming them where any is bound. This is not the guard and does not replace it: the finalizer still holds a configuration deleted by any other client, and it still holds one deleted through this endpoint in the window between the list and the write. It is there for the same reason `extensionMovesNothing` is there in [0027](0027-mutating-web-interface-behind-a-typed-writer-and-a-cross-origin-guard.md), which is that an endpoint answering `202` and then describing a teardown that is not going to start is worse than one that says what is in the way. Where nothing is bound the answer is `202` and a detail saying the controller was asked, because the finalizer runs after the response.

**Editing is allowed while leases are bound, and the asymmetry is the point.** Deleting removes horizon's ability to tear a lease down. Editing does not: the controller rebuilds the provider from the configuration on every pass, so a rotated credential is picked up by the next reconcile of every bound lease, and a machine already running keeps the lifetime backstop it latched at creation whatever the new `maxLifetime` says. The asymmetry is therefore between an act that takes a capability away and an act that changes which credentials that capability uses, not between a small change and a large one.

**`PUT`, and a whole-spec replace.** The body is the whole of `spec`, so a reference omitted is a reference cleared rather than one silently left alone, and submitting the same body twice leaves the same object. `PATCH /api/leases/{name}` already means a partial change in this API, where an extension moves `spec.duration` and nothing else, and using the same verb for a whole-object replacement would make one verb mean two things across four routes. The route answers with the summary of what was stored, as create does.

**The compare and swap belongs to `Replace`, not to the handler.** The implementation reads the configuration, builds a merge patch against what that read returned, and sends it under the `metadata.resourceVersion` that read saw, exactly as `Extend` does and for the reason [0027](0027-mutating-web-interface-behind-a-typed-writer-and-a-cross-origin-guard.md) recorded when the first attempt put the comparison in the handler: an invariant that lives in one caller is not an invariant. Two operators rotating different fields against the same read cannot net out into a spec neither of them submitted; the second is refused with `409` and told to read the configuration again. The endpoint does not retry underneath the caller, because a retry would apply a spec against a base the caller never saw.

**The summary carries the spec, in the shape a write accepts.** `providerConfigSummary` gains `spec`, built from the same Go type the create and replace bodies decode into, so the edit form fills from exactly what it will submit and there is one conversion rather than two that can drift. The machines route already carries a summary per configuration and the create form already polls it, which is the reason [0033](0033-create-a-provider-config-from-the-interface.md) gave for not adding a second route to carry the `Ready` reason, and it holds here too.

The field is null where the stored configuration holds something that shape cannot express: an image chosen by id or by selector, the deprecated `imageSelector`, or a provider block this interface does not offer. A full-spec replace of a configuration the form cannot represent would rewrite it rather than edit it, so the interface says so and leaves it to `kubectl` rather than reshaping it. The whole watchdog policy is submitted in seconds for the same reason: a lifetime the form rendered in minutes could not fill a control exactly for a configuration holding a value that is not a whole number of minutes, and rounding it would rewrite a field nobody touched.

**The lease summary names the configuration it is bound to.** `leaseSummary` gains `providerRef`, so the edit page lists the bound leases from the lease list it can already read, and shows the consequence before either control is used rather than after the apiserver refuses.

**The user-facing role gains `patch` and `delete` on `providerconfigs`, and not `update`.** The replacement reaches the apiserver as a merge patch under a resourceVersion, so `update` is a verb nothing exercises, and granting it would widen the role past what the interface can do. That is the same shape as the `patch` on `capacityleases` that the extension needed.

## Options considered

- Refuse the delete in the web handler and add no finalizer. Rejected. It protects nothing against `kubectl`, and this project's own rules call that patching the symptom. The handler check that remains is about the honesty of the response, not about the guarantee.
- Refuse the delete at the apiserver with a validating webhook. It would hold for every client, and it costs a webhook server, a certificate, a failure policy and a new way for the cluster to break when horizon is down. A finalizer is already how the lease teardown guarantee is expressed here, and it needs none of that.
- Refuse only while an Active lease is bound. Rejected. A lease being torn down is the one that most needs the credentials, and a lease not yet accepted will need them within a reconcile.
- Block edits while any lease is bound, symmetrically with delete. Rejected. It would make credential rotation impossible for the length of a lease, which is the operational need this verb exists for, and the hazard it would be guarding against was closed when the backstop was latched per instance.
- Add a general `Update` or `Patch` verb to the seam. Rejected for the third time, and for the reason [0027](0027-mutating-web-interface-behind-a-typed-writer-and-a-cross-origin-guard.md) and [0033](0033-create-a-provider-config-from-the-interface.md) both gave: one verb of that shape hands every holder of the seam the ability to move any field of any object the caller's RBAC reaches.
- `PATCH` with a partial body, so a form could send only what changed. Rejected. A form that renders every field cannot tell an emptied field from an untouched one, so a partial body would make clearing a reference impossible through the only client this endpoint has.
- Take the optimistic lock in the handler, by reading the configuration and passing the revision to the writer. Rejected. That is the shape the extension endpoint had before it was corrected, and it holds only for the callers that remember to do it.
- Carry the spec on a provider config detail route instead of on the summary. The machines route already answers with every configuration and the interface already polls it, so a second route would be a second thing to keep in step.
- Reshape an unrepresentable configuration into what the form can hold, and submit that. Rejected. It is a silent rewrite of fields the operator never saw, in the one operation where the whole body is authoritative.
- Round a watchdog lifetime into whole minutes for the form. Rejected for the same reason: it changes a stored value as a side effect of opening an edit form.

## Consequences

Every `ProviderConfig` in a cluster running this controller carries a finalizer, so uninstalling horizon before deleting its configurations leaves objects that cannot be deleted until the finalizer is stripped by hand. That is the same trade `CapacityLease` already makes, and it is the trade that makes the guarantee a guarantee.

A `ProviderConfig` deleted with `kubectl` while a lease is bound now stays in the cluster with a deletion timestamp instead of disappearing. `kubectl delete` blocks rather than returning, which reads as a hang until the object is described, and `Deletable=False` with reason `LeasesBound` is what the description says.

The interface can now take away the credentials a future lease needs, which it could not before. It cannot take away the credentials a current lease needs, which is the distinction the finalizer draws and the reason the delete control is worth having at all.

A `501` from a provider config route now means the process holds no config writer, exactly as it did for the create route, and all three mutating routes answer it together. The detail route added alongside them is a read and answers no `501`. Both serving modes supply the writer, so the split is still about an embedder rather than an install.

`ProviderConfigWriterFor` takes a reader and a writer rather than a writer alone, because `Replace` reads before it patches. A process that could construct the seam from a bare `client.Writer` can no longer do so, which is the same direction [0027](0027-mutating-web-interface-behind-a-typed-writer-and-a-cross-origin-guard.md) moved `LeaseWriterFor` when `Extend` landed.

An adopter bound to the rendered role gains the ability to delete provider configurations without being asked. Splitting the role is the adopter's own edit, and `docs/serving-the-interface.md` says which verbs to drop for a read-only operator.
